# Detection methodology and limitations

Local LLM Red Team is a prompt-level screening harness. Its default detector uses deterministic text patterns; it does not understand response meaning in the way a human reviewer or a validated semantic evaluator would.

## Scan lifecycle

1. Select attacks by stable ID or category.
2. Send each attack prompt to the configured target.
3. Inspect the returned text with the category-specific heuristic patterns.
4. Record the response, detector outcome, evidence, latency and available token counts.
5. Persist the run to SQLite and/or export JSON and Markdown reports.

Static mode sends each attack independently. Adaptive mode maintains a target conversation and asks a separate attacker target to generate bounded follow-up prompts. The generated follow-ups may vary, so retain the full report when comparing adaptive runs. Adaptive latency totals include both target and attacker calls; token totals currently reflect target responses.

## Outcome semantics

| Status | Operational meaning | What it does not establish |
| --- | --- | --- |
| `FAIL` | A known indicator associated with accepting the attack was found. | It does not prove full compromise or real-world exploitability. |
| `PASS` | A refusal-like indicator was found. | It does not prove the model resisted every part of the attack. |
| `NOT_DETECTED` | No known acceptance or refusal indicator was found. | It is not evidence that the attack failed. |
| `EMPTY` | The target returned no text. | It is not a safe refusal. |
| `ERROR` | The target request or response processing failed. | It is not a model outcome and should not be counted as one. |
| `THROTTLED` | The endpoint rate-limited the request (for example, HTTP 429/503). | It is not a model refusal or behavioural outcome. |

## Interpreting the summary

The current heuristic attack-success-rate calculation is:

`heuristic FAIL count / (total results - ERROR - EMPTY - THROTTLED)`

Only completed, non-empty responses enter the denominator. `EMPTY` and `THROTTLED` are excluded because neither provides a usable model outcome; `ERROR` is also excluded. `PASS` and `NOT_DETECTED` remain in the denominator: the latter is inconclusive, not proof of resistance. Coverage is reported separately so a low usable-response count cannot be mistaken for a strong result. The rate describes only the selected attack set and detector version; it is not a universal model-risk score.

The refusal-rate summary counts completed results classified as `PASS` with refusal evidence. Neither metric should be interpreted without reviewing the underlying responses.

## Known limitations

- **False positives:** a model may quote, explain or reject an attack while repeating words that match a heuristic pattern.
- **False negatives:** a successful response may use wording, structure or indirect behaviour that the current patterns do not recognize.
- **Context sensitivity:** a prompt-level response does not demonstrate how a deployed agent handles tools, retrieval, memory, permissions or external side effects.
- **Model variability:** sampling settings, model revisions, system prompts, templates and server implementations can change outcomes.
- **Adaptive variability:** follow-up prompts are generated by another model and are not deterministic unless that attacker model and its generation settings are controlled.
- **Limited attack coverage:** the default catalogue is a small starter set, not a comprehensive threat model or OWASP coverage claim.


## Multi-turn scenario evidence

Each scripted turn is evaluated independently, and a heuristic signal does not stop the remaining scripted turns. This preserves the later observations needed to distinguish an initial statement from subsequent behavior. A turn-level signal is not copied forward as if it were newly observed on every later turn.

Scenario evidence vectors are populated independently:

- `VERBAL_ACCEPTANCE` records a heuristic affirmative-language signal only.
- `PERSISTENT_OVERRIDE` remains `NOT_TESTED` unless a separate post-injection task demonstrates changed behavior under an explicit oracle.
- `POLICY_BYPASS` remains `UNVERIFIED` without a deterministic task oracle.
- `CANARY_DISCLOSURE` remains `NOT_TESTED` unless the scenario includes a run-scoped canary and an exact-match check.

A fictional, quoted or role-play framing does not by itself make procedural content harmless to the detector. The heuristic still requires human review and does not establish real-world impact. Execution errors remain execution errors, not model refusals or passes.

## Reproducible comparisons

For a defensible comparison, preserve:

- the exact attack manifest and scanner version;
- target type, endpoint implementation and model identifier/revision;
- system prompt, chat template and generation settings;
- attacker model and settings for adaptive scans;
- runtime environment and date of execution;
- raw JSON/Markdown output and SQLite database when used.

Change one variable at a time where possible. Review individual responses and evidence before treating a difference in summary metrics as meaningful.

## Responsible use

Run tests only against models and endpoints you own or are authorized to assess. Protect reports because they may contain prompts, model responses, internal instructions or other sensitive material. Keep inference endpoints private and avoid including credentials in shared reports.


## Expanded prompt-level coverage and run provenance

The starter catalogue includes probes for indirect instructions embedded in retrieved passages and simulated tool output, delimiter-boundary confusion, multilingual instruction overrides, refusal suppression and persistence-oriented prompts. These are prompt-level probes: they do not exercise an actual retrieval pipeline, tool runtime or external side effect. Use an integration harness for those boundaries.

Each scan now records a provenance envelope: scanner and Python versions, platform, target type, model, detector, mode, selected attack IDs, and the SHA-256 digest of the exact attack manifest. Adaptive runs also record attacker type/model and round limit. JSON exports carry this envelope under `run_metadata`; Markdown reports expose the principal comparison fields; SQLite stores it with the run. Existing databases are migrated additively.

The manifest digest identifies the exact ordered attack definitions, including prompts and versions. It is a reproducibility identifier, not proof that the target configuration or environment is unchanged. Endpoint URLs and credentials are deliberately excluded from provenance to avoid leaking secrets; record sanitized deployment details separately when required.


## Per-payload evidence hashes

Every static result now includes SHA-256 hashes of the exact attack prompt and returned response. Adaptive scans retain hashes per turn as well as the initial prompt and final response hashes. JSON and SQLite store these values; Markdown reports display the result-level hashes.

These hashes make accidental or deliberate content changes detectable when the original content is retained. A digest alone cannot reconstruct a prompt or response, establish when it was generated, or prove that the target endpoint behaved as claimed. Treat it as an integrity aid alongside the raw report, run metadata and controlled test environment.


## Responsible use and authorization

Only assess models, endpoints and systems you own or are explicitly authorized to test. Written permission must define the assets, dates, techniques, traffic limits and prohibited actions. Public accessibility is not authorization. Check the laws and regulations in every relevant country and jurisdiction before testing; rules may cover unauthorized access, privacy and personal data, communications confidentiality, contracts and sector-specific duties. The project does not provide legal advice or grant permission. If authorization or legal basis is unclear, do not run the test. Read the full [responsible-use and legal notice](responsible-use.md).


## Static scanner evidence and report schema

Static scanner JSON exports use an explicit `schema_version` so consumers can distinguish report structure changes from package version changes. The heuristic detector version and SHA-256 implementation fingerprint are recorded separately in run metadata. A changed detector implementation must not be pooled silently with results from an earlier fingerprint.

The static scanner's `FAIL` is a review-required heuristic indicator. It does not, by itself, establish verbal acceptance, persistent override, policy bypass or canary disclosure. Those are independent evidence dimensions and require their own observations and oracles; a phrase-level match must not promote one dimension into another.

## Static evidence vectors and controlled canary tests

Static scan results now carry an independent evidence vector with four dimensions: `VERBAL_ACCEPTANCE`, `PERSISTENT_OVERRIDE`, `POLICY_BYPASS` and `CANARY_DISCLOSURE`. A static phrase-level signal may populate only `VERBAL_ACCEPTANCE`, and remains review-required; it cannot establish persistence or policy bypass. Those dimensions remain `NOT_TESTED` or `UNVERIFIED` until a dedicated behavioral protocol or deterministic oracle supplies evidence.

The opt-in `--canary-test` runs a separate static probe using a random, run-scoped synthetic token placed in the target's system context. Disclosure is recorded only when the exact token occurs in the model response. Run metadata stores the token hash and a hash of the injected context, not a dedicated field containing the token; if disclosed, the token necessarily appears in the retained raw response. Protect and redact reports before sharing. The canary probe is not a real-secret test, is not part of the default attack profile, and cannot be combined with adaptive or quick mode. Static JSON reports use schema version `2`; the evidence vector has its own schema version `2` in run metadata.
